## 1. 本体结构核对

10.4 是 **jar-in-jar** 封装：真正被 FML 加载的本体在

```
META-INF/jarjar/guzhenren-0.1-neoforge-1.21.1.jar
```

外层包不能直接作为 `javac` classpath（直接指向外层会报 `程序包 net.guzhenren.network 不存在`）。
构建脚本会自动抽取内层包到 `tianfu/build/base-104/guzhenren-inner.jar`。

| 项 | 值 |
|---|---|
| 内层 jar 大小 | 106,304,539 字节 |
| 内层 jar SHA256 | `B6D314D3810B8BC5FCFDBC4F588DB8721F0EFDFC14D27A0A06D88143A01FE2BC` |
| 与 10.20 内层相比 | **字节完全相同** |
| 与 `_crash3/basever/guzhenren-10.4.jar` 相比 | **字节完全相同** |

因此 10.4 与 10.20 在 Java 代码层面等价，`Guzhenren98Compatibility` 里已有的
`10.4/10.20` 档位直接适用。

## 2. 兼容指纹

构建脚本对 9 个注入/反射目标类做逐字节 SHA-256 门禁，全部命中 10.x 档位：

```
Base fingerprints: 9/9 match 10.4/10.20 baseline
```

其中与 9.8 不同的 3 个类：

| 类 | 10.4 实测值 |
|---|---|
| `UikongqiaoquedingProcedure` | `307F6645…AD74E37`（退化为薄壳，开窍仪式在 `UikongqiaoguanbiProcedure`） |
| `KE1Procedure` | `F0908D99…68D30A0DC` |
| `UIxiuliananjianProcedure` | `1060052B…89B7230B` |

指纹不一致时脚本直接拒绝出包，不会把 9.8 或其它版本误标成 10.4。

## 3. 版本相关语义

- **命格 5 人气系数**：从 `UIxiuliananjianProcedure` 字节探测，10.4 命中 `7.5E-4`
  （9.8 是 `1.0E-3`）。测试输出：

  ```
  [探测] 命格5 人气系数 = 7.5E-4（9.8 应 0.001，10.x 应 7.5E-4）
  ```

- **转世钩子**：10.4 的 `JingJieBaoCunProcedure` 仍是
  `execute(Event, LevelAccessor, Entity)`（4 参 Mixin 签名），
  与 11.22 的 `(Event, LevelAccessor, double, double, double, Entity)` 不同。
  本次构建使用 10.x 签名，已用 `javap` 核对。

- **开窍入口**：仍走 `UikongqiaoquedingProcedure.execute(LevelAccessor, Entity)`；
  10.4 中该方法是 26 行薄壳，TAIL 注入点仍可达。

## 4. 代码改动

本次**没有改玩法代码**，只补了目标化构建链路：

| 文件 | 改动 |
|---|---|
| `tianfu/tools/build-104.ps1` | 新增。自动抽取内层本体、9 类指纹门禁、`-g` 编译、打包 `tianfu-<version>-10.4.jar`、自检并输出 `build-report.json` |
| `tianfu/build.gradle` | `archiveClassifier` 改为可由 `-Ptianfu.archiveSuffix` 覆盖，默认仍是 `mc98` |
| `META-INF/neoforge.mods.toml` | 描述改为「适配 9.8 / 10.4 / 10.20」，不再写死 9.8 |

构建命令：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tianfu\tools\build-104.ps1
```

可选参数：`-BaseJar`（外层或内层 jar 均可）、`-Suffix 10.4`、`-MinecraftDir`、`-Jdk`。

输出命名统一为 `天命-<天命版本>-<适配本体版本>.jar`，例如 `天命-1.4.18-10.4.jar`；
游戏内 `displayName` 同时写成 `蛊真人天命（本体10.4）`。Gradle 构建可用
`-Ptianfu.archiveName=天命` 覆盖产物名（默认已是 `天命`）。

## 6. 实机反馈修复（第二轮）

实机日志确认 10.4 指纹校验通过；玩家存档里出现「无法最终确认」的状态：

```
kongqiao = 0
purchased = [v2_aptitude_shackled, v2_luck_forfeit, v2_routi_canque,
             zhenyuan_bujie, feixingdao, ji_wanshi_bumie, jingli_ruhai]
```

`v2_aptitude_shackled`（空窍桎梏）在 `kongqiao=0` 时把资质锁在 0，界面因此判定
「尚缺结算根基」，最终确认按钮被禁用；同时旧 `closeBlocked()` 在缺锚点时放行，
形成「能关但不能确认」的错位。

本版改动：

| 位置 | 改动 |
|---|---|
| `TianfuApply.settleSelection` | 空窍桎梏也算结算根基；不再因 `kongqiao=0` 直接判 `CONFLICT` |
| `TianfuApply.applyBaseEffects` | 桎梏 + 未选任何资质时，按 **丁等（kongqiao=8）** 跑本体原生结算，再锁定 8 |
| `TianfuViewScreen.hasAnchorSelection` | 桎梏计入锚点，确认按钮可用 |
| `TianfuViewScreen.closeBlocked` | 改为**硬门禁**：只要还有已购条目或未接受的随机候选，Esc / × / `onClose` 都不放行 |
| `TianfuViewScreen` | 新增「放弃候选」按钮；随机候选不再造成永久锁死 |
| `TianfuRollDiscardPayload` | 新增 C2S 包，清空 `rollpending`，不扣点、不返还摇取次数 |
| `TianfuConfirmPayload` | 拒绝原因从 actionbar 改为聊天栏可见，并写入服务端 WARN 日志 |
| `TianfuMod` | Payload registrar 版本 `1` → `2`（新增包，客户端/服务端必须同版） |

`空窍桎梏` 的描述同步改为「未选资质则按丁等锁定；撤销需返还 8 点」。
这样既保留 `-8` 的补点，又不会出现「锁 0 → 永远不能确认」的死档。
