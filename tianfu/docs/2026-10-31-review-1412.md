## 三、`wenyangStep` 被加固了（这是核心改进）

1.4.12 版完整逻辑（反汇编还原）：

```java
if (!isFinite(jindu) || jindu <= 0)                  return dangqian;
if (!isFinite(dangqian))                             return 0;
if (!isFinite(xiulian))                              xiulian = 0;
if (dangqian >= jindu - max(1e-8, ulp(jindu) * 8))    return jindu;   // 近满容差
if (xiulian > 0)                                     return clamp(dangqian + xiulian, 0, jindu);
if (xiulian < 0 && dangqian < jindu)                 return max(0, dangqian + xiulian);
return dangqian;
```

### 对照实测（同一套 14 条测试，分别跑两个 jar）

| 用例 | 1.4.11（我方） | 1.4.12 |
|---|---|---|
| `dangqian = 399.999999999`（浮点漂移） | **FAIL** 保持原值 → 本体 `==` 仍判不等 | PASS 吸到 400 |
| `dangqian = Infinity` | **FAIL** 返回 400 | PASS 归 0 |
| `dangqian = NaN` | **FAIL** 返回 NaN（会污染存档） | PASS 归 0 |
| `xiulian = Infinity` | **FAIL** 返回 400（白送 300 进度） | PASS 当作 0 |
| 合计 | **10 / 14** | **14 / 14** |

也就是说：**我 1.4.11 的修复只处理了「冲过头」，没处理「差一点点」**。
而本体判定突破是 `dangqian == jindu` 精确相等，浮点漂移一样会被卡住 ——
1.4.12 用 `max(1e-8, ulp(jindu)*8)` 的近满容差把这个洞补上了。

容差取值也合理：只兜浮点误差，`399.99999`（差 1e-5）不会被吸，不会凭空送进度。

## 六、需要注意的三点

1. **`@At("TAIL")` 的老问题**：TAIL 只锚在方法**最后一个** return。
   `Xiulianjingjie…execute` 有多条 return 路径，走别的 return 时那次对齐不会跑。
   不过 `CultivationButtonMixin` 在 `UIxiuliananjianProcedure` 的 **HEAD** 也做了一次，
   「点突破」这条关键路径被覆盖，等于双保险。

2. **注入是懒验证的**：那两个过程类要到玩家真正打坐 / 点突破时才加载，
   所以「服务端起得来」不等于「注入一定成功」。静态核对（目标类存在、签名一致、
   HEAD/TAIL 必可解析）风险很低，但**第一次进游戏打坐才是真验收**。

3. **`healPhysique` 变得更强硬**：只要 `tizhi` 与已购不符就改回来。
   按 tianfu 的模型（买的体质永久有效）这是对的；
   但如果本体将来出现合法的「体质变更」机制，tianfu 会每 20 tick 覆盖它。
