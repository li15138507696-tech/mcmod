# 蛊真人 9.8 适配（tianfu 1.2.34 / daotu 1.5.2 / malice 1.0.4）

## 一、9.8 与 10.x 的差异只有一个类

用 9.8 本体（`guzhenren蛊真人模组本体9.8.jar`）直接试编译三个模组，错误只有一处：

```
找不到符号: 类 UikongqiaoguanbiProcedure（net.guzhenren.procedures）
```

- **10.x**：空窍收尾结算被拆到新的 `UikongqiaoguanbiProcedure`；
- **9.8**：根本没有这个类，收尾还在 `UikongqiaoquedingProcedure` 里；
- **10.x 的 `queding`**：只是「先调 `guanbi.execute`、再 `closeContainer`」的薄壳（已 javap 核对）。

所以 **`queding` 是两个版本都存在的稳定入口**。

## 二、改法：注入点从 guanbi 换成 queding

| 文件 | 改动 |
|---|---|
| tianfu `TianfuOpening` | `UikongqiaoguanbiProcedure.execute` → `UikongqiaoquedingProcedure.execute` |
| tianfu `mixin/UikongqiaoquedingProcedureMixin` | 新文件（原 `UikongqiaoguanbiProcedureMixin` 删除） |
| daotu `mixin/UikongqiaoquedingProcedureMixin` | 同上 |
| 两个 `*.mixins.json` | 类名同步 |

**一份 jar 同时兼容 9.8 与 10.x**，不再需要外部兼容补丁。

### 顺手修掉的一个坑

tianfu 的 `javac_check.py` 原来**不清理** `javac_out`：源码删掉/改名后旧 `.class` 会一直留着并被打进 jar。
这次就出现了「新 mixin 已改名，jar 里还躺着引用 `UikongqiaoguanbiProcedure` 的旧类」——
在 9.8 上只要被加载就是 `NoClassDefFoundError`。已加编译前清空输出目录。

## 三、三个模组的结论

| 模组 | 9.8 编译 | 改动 |
|---|---|---|
| 天命 tianfu | ✅ exit 0 | 注入点 + 调用改名 |
| 道途 daotu | ✅ exit 0 | 注入点改名 |
| 恶意 malice | ✅ exit 0（需 l2hostility + 内嵌 l2core） | **无需改动**：字节码里完全没有引用 guzhenren 的类 |

## 四、兼容性验证

同一份源码分别对 9.8 与 10.4 本体编译，四次全部 exit 0：

```
tianfu vs 9.8   exit=0   sources=46
tianfu vs 10.4  exit=0   sources=46
daotu  vs 9.8   exit=0   sources=33
daotu  vs 10.4  exit=0   sources=33
```

产物：`tianfu-1.2.34.jar`（191,767 B）、`daotu-1.5.2.jar`（100,146 B），
已装进 9.8 服务端 mods 与 10.4 客户端整合包 mods，两侧 SHA256 一致。

## 五、g98compat 补丁

9.8 服务端原本放着一个外部补丁 `蛊真人9.8兼容补丁-g98compat-1.0.0.jar`（把调用重定向到 queding）。
现在模组已原生适配，补丁不再需要，而且它的 `TianfuOpeningMixin` 注入的是「调用 guanbi」那一行——
该调用已经不存在，留着有注入失败风险。已改名为 `.jar.disabled`（随时可改回来）。

## 六、诚实说明

**游戏内未实测。** 已验证：两版本体编译通过、jar 结构正确、mixin 配置与类一致、无残留旧类、哈希一致。
需要实测的是：9.8 下用希望蛊开窍后，天命界面是否照常弹出、道途是否记到「已开窍」。
