## 0. 一句话

开局骰出空窍档位（十绝体／甲／乙／丙／丁）：

- **十绝体** → 不弹附属界面，**仅**以 1/11 概率随机到附属新增的「**杀神**」（第 11 种十绝体）；
- **甲/乙/丙/丁** → 弹**购买界面**，按档位拿到**天赋点数**，从「全池」**自由购买**天赋（含 18 个「凡体」体质与 20 条词条），专补低档空窍天赋的短板。

## 2. 数据模型

全部存玩家 `PersistentData` 的自有子标签 `tianfu`（不占本体 `PlayerVariables` 字段）：

| 键           | 类型       | 含义         |
| ----------- | -------- | ---------- |
| `pending`   | bool     | 待购买（界面已弹出） |
| `points`    | int      | 本档位总点数     |
| `used`      | int      | 已用点数       |
| `purchased` | String[] | 已购条目 id    |
| `applied`   | bool     | 已结算        |
| `slay`      | int      | 杀戮值（仅杀神）   |
| `slayDay`   | long     | 上次重置的日戳    |

词条/体质条目定义采用**数据驱动一张表**：`id / 名称 / 类别（体质|词条）/ 品质 / 成本 / 施加类型 / 数值 / 低档权重`。

## 3. 开局时序（唯一 Mixin）

```
关闭开窍界面 → UikongqiaoguanbiProcedure（本体原逻辑照跑）
   ↓ TAIL 拦截（@Inject at=TAIL, require=0, remap=false, try-catch 静默放行）
   if (tianfu.applied) return;
   if (kongqiao == 3.0) {                       // 十绝体：只做杀神随机
        if (random() < 1.0/11.0) vars.tizhi = 54.0;   // = rand(1..11) 的等价实现
        set applied; return;
   }
   // 甲/乙/丙/丁 → 弹购买界面
   points = 按档位(甲12/乙10/丙8/丁6); set pending + points
   GuzhenrenMod.queueServerWork(10, () -> 打开购买界面)
   ↓ 玩家购买并提交（TianfuActionPayload）
   服务端校验（点数不超支、体质类 ≤1）→ 应用 → 置 applied
```

**为什么这样实现杀神随机**：本体那段是巨型方法里的 `Mth.nextInt(random,1,10)`，用 `@Redirect` 定位太脆；改为 TAIL 里以 1/11 概率覆写，数学上等价于 `rand(1..11)`（杀神 9.09%、其余各 9.09%），且**只有一处 Mixin**。

### 8.1 回复乘区口径（2026-10-20 修正，勿回退）

真元／念头回复**不是**「基准 + 基准×各词条」的加性叠乘，而是：

```
mult = max(0.0, 1 + Σ词条百分比)      // 负分项只压乘区，地板 0
每tick回复 = 自然回复基准(0.0001) × mult  +  正项（凝练/体质等）
```

- **旧实现的坑**：`0.0001 + 0.0001 × (−0.30)` 在只买负分项（真元枯竭／念头干涸）时净值为负，
  `clamp` 只挡下限 0 → 玩家真元被持续抽到 0，观感「负增长」。
- **新口径**：负分项最多把自然回复**抹平到 0**，永远不会把资源往外抽。
- 与加性叠乘的差异仅在负分项场景；正分项场景两者完全一致（都等于 1 + Σ）。

### 8.2 气运口径（2026-10-20 修正，勿回退）

**所有气运词条一律只写 `qiyun_shangxian`（上限），不直接写 `qiyun`。**

本体 KE1 每秒执行一次（`_reverse/KE1Procedure.txt:292-297`）：

```java
if (qiyun_shangxian < qiyun) { qiyun = qiyun_shangxian; }   // 只向下削平
```

- **旧实现的坑**：`qiyun_shangxian` **只被读取、从不被本体覆写**（全库 8 处引用皆读取），
  但上面的削平是**单向**的 —— 直接 `qiyun += N` 而不抬上限，下一秒就被削回旧上限，
  点数白给。最坏场景是低上限机缘（丁等 `qiyun_shangxian` 仅 1–10）：
  `气运微光 +5` / `气运微荫 +12` 完全不可见，即「有的气运效果无法生效」。
- **新口径**：抬上限而非注水。上限抬高后，本体每分钟 `qiyun += 0.05` 的自然回复
  会逐步填满新空间（丁等 cap=5 时，+12 上限在 1 小时内即可自然回满）。
- **`qiyun` 从负数起跳的修正**：`气运稀薄 −15` 叠加低上限机缘会把上限算成负数，
  而本体不校验 → `qiyun` 被硬压成负数。所有上限写入统一经 `TianfuEffects.addCap` /
  `TianfuTalents.tryAdd` 兜底 `max(0, ·)`。
- **负词条本就生效**：削平是单向的，所以 `气运稀薄 −15`（压上限）一直有效，
  无需特殊处理；只有正向词条会失效。
- **撤销对称**：`revokeOnce` 对同一上限做等量反向，`apply → revoke` 精确回到原点。

## 9. 购买界面（自绘 Screen · 借鉴觅长生）

觅长生创建角色界面是**「点数余额 + 可购条目列表（带成本、实时勾选、即时扣点）」**，本附属照此做：

- **顶部**：点数余额 `剩余 / 总`、档位（甲/乙/丙/丁）
- **主体**：可购条目**列表**（按 品质/类别 分组，可滚动），每行显示：名称 / 品质 / 成本 / 效果摘要；点击 = 购买或取消（实时更新余额）
- **约束提示**：体质类只允许 1 个（已选后其余体质置灰）；点数不足的高价条目置灰
- **底部**：「确认」按钮（提交）＋「重置」
- **服务端权威**：界面渲染用 `TianfuStatePayload` 下发（池子定义 + 点数），点选只发**已购 id 列表**，服务端校验（超支/体质数）后落库
- 遵守自绘铁律：命中区只由 `layout()` 赋值、单一 `R(x0,y0,x1,y1)`+`has()`、单一 `hitOrder`、F6 命中叠加层

### 9.1 描述换行（2026-10-20 修正，勿回退）

词条描述**不再单行截断**，改为按面板宽度贪心换行 + 行高自适应。

- **旧实现的坑**：描述固定画在 `left + 82`、可用宽 `right - left - 88`（标准面板 316px → 228px）
  单行绘制，超宽即被 `fit()` 截断补「…」。164 条描述里有 12 条超宽（最长 369px，
  甲等机缘），玩家看到的是半句话 —— 即「有的词条描述无法显示」。
- **新口径**：`wrapDesc()` 按字符增量累加宽度断行（**不是**每步 `substring` + `font.width` 重算），
  断点优先落在 `、，；）。` 之后，避免把相邻子句从中间劈开；最多 `MAX_DESC_LINES = 3` 行，
  余量并入末行由 `fit()` 兜底，保证极窄面板也不溢出。
- **行高自适应**：`rowHeight(row)` = `ROW_H + (行数−1) × LINE_H`（20 / 30 / 40px）。
  `layout()` 的总高累加与 `y += h` 赋值**必须都用 `rowHeight()`**，否则滚动条与命中区错位。
- **缓存**：`wrapCache` 以「面板宽 + `\0` + 原文」为 key，`layout()` 与 `render()` 共用同一份
  断行结果 —— 既省重复测量，也保证行高与绘制严格一致。
- **徽章/按钮不随行高拉伸**：已购徽章与撤销按钮固定 16px 高、按行中线居中。
- 实测：面板宽 316→120（描述列 228→32px）逐档验证，**丢字 0、溢出 0**，
  原先被截断的 12 条全部完整显示。
