# 天命 · 「命运由天」随机天赋生成 设计（tianfu 1.2.35）

## 一、要解决的问题

现有开局只有一条路：选难度领点数 → 自己逐条买。玩家希望能二选一——
要么自己配，要么让系统摇一份，且摇出来的强度仍由难度决定。

## 二、必须先承认的硬约束

### 2.1 「十绝体 + 机缘都必选」字面上做不到

| 难度 | 点数 | 十绝体(16) | 甲机缘(16) | 乙机缘(12) | 丙机缘(8) | 丁机缘(5) |
|---|---|---|---|---|---|---|
| 顺天应命 | 24 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 凡尘问道 | 16 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 逆天争命 | 12 | ❌ | ❌ | ✅ | ✅ | ✅ |
| 万劫磨道 | 8 | ❌ | ❌ | ❌ | ✅ | ✅ |

12 / 8 点档连一个十绝体都买不起。

**采用口径：必含「1 个资质」= 十绝体或机缘，二者取一。**
这同时是最终确认的门禁（`TianfuConfirmPayload` 要求至少 1 个 SIJUE/JIYUAN）——
不保证的话随机完会直接卡死，无法确认。

十绝体只在 `点数 ≥ 16` 时进入第一层候选；12 / 8 点档它被剔除，只剩机缘档可抽。

### 2.2 不能复用「买 / 撤」来实现重摇

`TianfuApply.revoke` 明确拒绝 SIJUE / JIYUAN（本体原生写入不可回滚）。
所以「随机落库 → 不满意全撤 → 重摇」这条路是死的。
必须走 **待定预览 → 一次性落库**。

## 三、玩家流程

```
选难度那一屏
  ├─ 直接点难度行 ─────────────→ 现有自定义流程（发点，自己买）—— 一字不变
  └─ 先点亮「命运由天 · 随机生成」→ 再点难度行
                                  → 服务端摇一份 → 预览
                                  → 「再摇一次（剩 N 次）」/「接受此命 · 锁定本世」
```

- 点亮开关后点难度行，弹出的是**随机确认**模态（提示「随机后本世锁定」）。
- 已选难度的存档无法再摇：随机是二选一的另一条路。
- 摇出结果后**不能手动增删**（用户口径）。接受 = 立即 `markConfirmed` + `markSettled`。

## 四、随机算法（贪心花光）

```
budget = 该难度点数（首次摇 = 难度发放的点数；重摇 = 当前余额）
① 第一层（资质类别）：候选 = {十绝体} ∪ {甲, 乙, 丙, 丁}，每候选一个槽位、等概率
   · 买不起的候选先剔除，剩下的重新归一化
   · 抽中「十绝体」→ 进入第二层
   · 抽中某个机缘档 → 直接取该档（每档只有一条）
② 第二层（十绝体内部）：在 11 个十绝体里再抽一次（1/11）
③ 凡体（体质唯一；抽到十绝体则跳过）
   · budget ≥ 3 且 rng < 0.70 → 随机一个凡体
④ 词条贪心（上限 64 轮，防「负词条→预算变大→继续抽」死循环）
   · 候选 = 池内未买 + 买得起（负成本永远买得起）
   · 按成本加权：weight = max(1, 18 - cost)；负成本 weight = 1（稀有）
⑤ 没有任何买得起的条目 → 结束
```

第一层槽位分布（1000 次/档实测）：

| 难度 | 点数 | 可负担槽位 | 分布 |
|---|---|---|---|
| 顺天应命 | 24 | 5 | 十绝体 20.2% / 甲 21.2% / 乙 20.8% / 丙 18.5% / 丁 19.3% |
| 凡尘问道 | 16 | 5 | 十绝体 19.4% / 甲 22.0% / 乙 21.0% / 丙 19.2% / 丁 18.4% |
| 逆天争命 | 12 | 3 | 乙 33.2% / 丙 32.5% / 丁 34.3% |
| 万劫磨道 | 8 | 2 | 丙 50.6% / 丁 49.4% |

净成本 = `点数 - 剩余 budget`，可能小于点数（无可购项时）。

## 五、服务端状态机

NBT 新增两个键（仍在 `tianfu` 子标签内）：

| 键 | 类型 | 用途 |
|---|---|---|
| `roll` | int | 已摇次数，上限 `TianfuRoll.MAX_ROLLS` = 3 |
| `rollpending` | list&lt;str&gt; | 待接受的条目 id，接受前不落 `purchased` |

新增两个包：

| 包 | 触发 | 门禁 |
|---|---|---|
| `TianfuRollPayload(difficultyId)` | 首次摇 / 重摇 | 已开窍；未确认；首次要求难度未选；重摇要求 pending 非空且 roll < 3 |
| `TianfuRollAcceptPayload()` | 接受此命 | pending 非空；未确认；含资质；净成本 ≤ 余额 |

首次摇与重摇走同一个包：`pending` 为空 → 首次（设难度 + 发点 + 生成），
`pending` 非空 → 重摇（不重复发点）。`difficultyId` 在重摇时被忽略。

接受时复用现有确认链路：

```
TianfuData.applyRoll(ids, netCost)   // 原子：写 purchased + 扣点 + 清 rollpending
→ markDeferred
→ TianfuApply.applyAllConfirmed(false)
→ markConfirmed + markSettled
```

## 六、客户端 UI

改动全部集中在 `client/TianfuViewScreen.java`：

1. **难度屏**：右侧（`y 44..62`，与「最终确认」按钮同位置，但两者互斥显示）加一个可点亮/熄灭的
   按钮「命运由天 · 随机生成」。点亮后点难度行 → 走随机确认模态。
2. **预览态**：`pendingRoll` 非空且未确认时，列表切为只读抽签结果
   （每条一行，复用 `Row.spec`），底部固定两个按钮：
   - 「再摇一次（剩 N 次）」—— 次数用尽置灰
   - 「接受此命 · 锁定本世」
3. `layout()` 仍是命中区的唯一赋值点，新按钮走同一套；预览态时 `listBottom` 上移让出按钮条。

`TianfuStatePayload` 扩两个字段：`rolls`（int）、`pending`（list&lt;str&gt;）。

## 八、不做（YAGNI）

- 不做随机后手动微调（用户明确要锁定）
- 不做随机种子 / 结果回放
- 不动 `TianfuPool.Kind` 枚举顺序（附属依赖 `ordinal()`）
- 不新增物品 / 贴图 / 数据包资源
