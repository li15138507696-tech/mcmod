## 批次 A：炼蛊窗口 + 突破口径（P0-2 / P0-3 / P0-7 / P0-8）

### A-1 `TianfuEffects.java` 投料窗口取并集（P0-7）

**改前**
```java
boolean inFeedWindow = cur >= 50.0 && cur <= 70.0;
```
**改后**
```java
boolean inFeedWindow = (cur >= 20.0 && cur <= 40.0) || (cur >= 50.0 && cur <= 70.0);
```

**依据**：本体 792 个完成型过程分三族 —— A 族 347 个（只有 50–70）、**B 族 351 个（20–40 与
50–70 两段都必投）**、C 族 94 个（无窗口）。

**后果（旧逻辑）**：B 族第一段窗口被压缩；更糟的是 `p == 40` 的边界失败判定会被跳过，
玩家失去「炼制失败」提示，却在 `p == 100` 时因 `中途加材料1 != 1` 而**整段跳过结算**
→ 进度清零、材料与魂魄静默全损。

### E-2 `Op.DAOHEN_MAIN`：只写主修那一路

```java

```

`TianfuV2Store.migrate()` 在补建 Receipt 之后、写盘之前，加一段下架退款：

```java
List<String> purchased = new ArrayList<>(current.purchased());
int points = current.points();
for (String id : List.copyOf(purchased)) {
    Integer floor = TianfuTalents.retirementRefund(id);
    if (floor == null) continue;
    Receipt receipt = receipts.get(id);
    // 按 Receipt 的**原成交价**退；没有成交账时退下架表里的固定值。
    // 绝不按「当前目录价」推算——那样会给历史玩家多退或少退。
    int refund = receipt != null ? receipt.paidCost() : floor.intValue();
    if (refund > 0) points += refund;
    purchased.remove(id);
    receipts.remove(id);
}
writePurchased(tag, purchased);
tag.putInt(KEY_POINTS, points);
tag.putString(RETIRED_KEY, ...);   // v2_retired 审计留痕
```

**幂等三道保险**：
1. 退掉的条目从 `purchased` 移除 → 下次扫描再也找不到它；
2. `SCHEMA` 台阶（`>= 3` 时 `migrate()` 开头就早退）；
3. `v2_retired` 写进存档，可肉眼核对。

**触发点**：`migrate()` 现在在 `buyReason` / `revoke`（批次 D 加的）以及原有的
`openSelection` / `applyAllConfirmed` 里调用 → 玩家**任何一次交互**都会触发一次迁移。

**键一致性已核**：`TianfuV2Store.KEY_POINTS = "points"` 与 `TianfuData.points()` 读的是同一个键，
`migrate` 写点不会写坏旧字段。

## 批次 I：P2 收尾（漏洞 / 逻辑 bug / 上限）

### I-1 P2-6 `planRoll` 补点预算泄漏（**真漏洞**）

旧实现 `if (negativesPicked >= 6 || working.negativeGrant() >= 12) break;` —— 12 点是**买前**判据，
最后一条会把总额顶过去。T6 用 DP 穷举 `{8×3, 5×5, 2×12}` 实测可漏到 **19 点**，
一旦超过 `NEGATIVE_CAP=24` 整批会被 `acceptRoll` **整批拒绝** → 玩家白耗一次摇号。

改为**买前按本条全额预测**，超预算就跳过这一条（继续找更小的），绝不越界：

```java
if (working.negativeGrant() + Math.max(0, -negCost.intValue()) > RANDOM_GRANT_BUDGET) {
    continue;
}
```

**实测**（`RollBudgetTest`，120 个随机种子）：最坏补点 **≤ 12**，且**每一批都能被
`acceptRoll` 整批接受**（不再出现白耗摇号）。

### I-2 P2-5 恶意组门槛绕过（**真漏洞**）

旧实现只在 `TianfuPool` 注册层过滤，而 `planRoll` 遍历的是 `TianfuTalents.all()`，

### I-3 P2-11 恶意·适应「首击即叠层」

`stacks.merge(key, 1, Integer::sum)` 先加再取 `cur`，导致第一次被同类伤害就吃到 1 层减免。

## 批次 J：乘算累积类的上限（本体基值追踪）

任务书要求「不能只改描述不改实现」，所以这 5 个族的封顶**真的做了**，而不是只写文案。

### J-1 为什么必须追踪“本体基值”

这 5 个族的效果是**乘算/加算累积在同一个本体字段**上的，例如魂魄上限：
`hunpo_lianxi ×1.15` → `hunzai_kuanhou ×1.15` → `hunpo_rugui ×1.5` → `shen_hunxi_zhuzai ×2.0`
连乘到 **3.97×**。写死一个绝对值是错的（每个玩家基值不同），正确做法是：
**结算前记下本体基值 → 应用后按「基值 × mult」或「基值 + add」钳回**。

### J-2 `TianfuTalents.FIELD_CAPS`（字段级，基值相对封顶）

| 字段 | 上限 | 依据 |
|---|---|---|
| `qiyun_shangxian` | **基值 × 3.0** | 连乘 1.12×1.18×1.40×1.30×1.80 ≈ 4.34× |
| `zuida_hunpo` | **基值 × 3.0** | 连乘 ≈ 3.97× |
| `hunpochengzaijixian` | **基值 × 3.0** | 同上 |
| `shouyuan` | **基值 + 300** | +80 / +200 / +50 = +330 |

实现：
- `snapshotCapped(v)` 在 `applyOnce` 开头取基值快照；
- 每个 `FIELD_MULT` / `FIELD_ADD` 写完立刻 `clampField` 钳回；
- **基值为 0 时不做倍数封顶**——0×任何倍数仍是 0，而本体「零上限保持零」的自然行为要保留，
  这样 `fuze_mianchang`（+15）在零上限玩家身上仍按原逻辑不生效，不会被误封顶。

钳制算术抽成 `limitFor(name, base)`（纯函数），因为 `clampField` 需要
`PlayerVariables` 的运行时实例（静态初始化依赖游戏注册表），没法直接单测。

### J-3 生命上限：封顶点定在**唯一合成处**

第一次尝试把 `Math.min(4.0, health)` 放进 `TianfuTalents.attrs()` —— **测试立刻抓到不对**：
`attrs()` 只含扩展词条（血气如林 1.2 × 万世不灭 2.5 = 3.0），
而池内 `shen_bumie_jinshen ×2.0`、`jingu_qiangjian ×1.1` 是硬编码在 `TianfuAttributes` 的，
根本没过 `attrs()`。所以 3.0 永远碰不到 4.0 的顶，等于没封。

正确落点：`TianfuAttributes` 里的 `health *= talent.healthMult();` 之后 ——
那是**所有生命来源的唯一合成点**（池内 2.2 × 扩展 3.0 = 6.6 → 钳到 4.0）。
`attrs()` 恢复为「只返回裸值、不封顶」，并在注释里写明封顶在哪。

### J-4 真元恢复：护栏式封顶

`TianfuTalents.regenZy` 原来是 `sum(REGEN_ZY)`，封顶 **+300%**。

今天不改变任何数值，只保证以后加条目不会把真元恢复到离谱。
