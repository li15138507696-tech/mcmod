## 一、四项决定性新发现（其余所有结论都由它们推导）

这四条是本轮审查最有价值的部分，任务书没有提到，但直接决定方案怎么定。

### 发现 1｜本体道痕互斥公式已完整存在，且用 `daohen_zong` 当"异道"分母

`ShangHaiLiuCheng1Procedure:27-30`（**主伤害流水线**）与 `BuffLiuCheng1Procedure:46-54`（蛊虫/投射物流水线）是**同一套公式**：

```java
A = own/1000 - (daohen_zong - own)/1000;   // own = 本次所用流派的道痕
B = (daohen_zong - own)/1000 - own/1000;
A = max(0,A); B = max(0,B);
最终伤害 = 基础 × (1+A)(1+C) / ((B+1)(D+1)) × (1 + Σbuff放大器)
```

`LiuPai1` 的实参是**该流派 `daohen_*` 原值**（`Chun4DanSheWuJiZhongShiTiShiProcedure:50` 传 `dahen_zhoudao`）。

**换算成人话**：`own = 本流派道痕`，`other = 其余 43 路之和`，
- 专精：`A = own/1000` → 伤害 **×(1+own/1000)**
- 杂修：`B = (other−own)/1000` → 伤害 **÷(1+B)**

| 道痕分布 | 伤害倍率 |
|---|---:|
| 单流派 1000 | **×2.00** |
| 单流派 2000（十绝体级） | **×3.00** |
| 双流派各 1000 | ×1.00（专精收益归零） |
| 三流派各 1000 | ×0.50 |
| 均摊 44 路共 13200（**五行道藏**） | **×0.074** |
| 均摊 44 路共 66000（**神·万道归宗**） | **×0.0156** |
| 均摊 44 路共 132000（**极·众道至尊**） | **×0.0079** |

→ **这三个"神级/极级"天赋当前不是超级增益，而是把玩家削成废人的陷阱**，而且分别标价 5 / 12 / 16 点。
→ 任务书要求「改成只加主修」**是唯一正确的修复方向**：加主修时 `other = 0`，`A` 直接线性涨，天赋才第一次真正变成增益。
→ 不需要（也不允许）另写五行相生相克——本体没有任何生克代码。

### 发现 2｜`daohen_zong` 是每 tick 重算的派生值 → `zonghen_chubei` 是死天赋

`KE1Procedure:844-891`：

```java
if (tizhi != 11.0) {
    daohen_zong = daohen_yudao + dahen_zhoudao + … + daohen_bianhuadao;   // 恰好 44 项
}
```

求和清单实测 **44 项**，与 44 个字段一一对应，无遗漏、无重复。

→ `zonghen_chubei`（`TianfuTalents:190`，天/5 点）写 `daohen_zong += 300`，**下一 tick 被整体覆盖 → 净效果恒为 0，白扣 5 点。**
→ 反过来：`TianfuTalents.allDaohen` 显式跳过 `daohen_zong`、只写 44 个字段（`:714-719`），这是**对的**，不需要改。

### 发现 3｜至尊仙体（本体名：**至尊仙胎体**）= `tizhi 11`，其"不互斥"就是跳过上面那次重算

`UishuxingshijuetiProcedure:31-32` → `tizhi == 11.0` 返回「至尊仙胎体」。本体体质表是 1–16：1–10 十绝体、**11 至尊仙胎体**、12 纯梦求真体、13 气运之子、14 天外之魔、15 正道善德身、16 无。

`tizhi == 11` 时 `daohen_zong` 冻结 → `other` 变成负数 → `A = 2·own/1000`（**双倍优势**）、`B` 恒为 0（**零劣势**）。
→ 至尊仙胎体不只是"不互斥"，是**A 翻倍 + B 归零**，比普通玩家强得多。
→ `tianfu` 目前**没有**发放 tizhi 11（凡体 17–53、十绝体 1–10、杀神 54），符合任务书原则 9。**1.4.18 必须加断言锁死**，否则将来有人加个体质就白送这个特权。

### 发现 4｜本体的"突破成功率"P **不是概率**，是一个 [−2,+2] 的线性分

`UIxiuliananjianProcedure`（4 个尝试点，形状一致）：

```
P = 1 − 0.1×转数 − 0.1×转数² + 0.0002×真元上限 + 0.01×气运 + k×人气
k = 7.5e-4 (命格==5) / 5.0e-4 (其余)
判定：Math.random() < P       本体不对 P 做任何 clamp
```

| 转数 | P（常规配置） |
|---:|---:|
| 1 | +1.060 |
| 2 | +0.660 |
| 3 | +0.060 |
| 4 | **−0.740** |
| 5 | **−1.740** |

→ 三转起 P 就跌破 0，**四转之后本体判定"必失败"**。
→ 现有附属实现是「失败率乘算」`P' = 1−(1−P)(1−r)`，当 `P = −0.74`（数学上等于 0%）时**恰好等于 r**。也就是**把"不可能"变成"有 r 的概率"**。
→ 由于 `Σr` 是纯加法且无上限：`突破通天0.30 + 厚积薄发0.20 + 修炼如神0.40 = 0.90`（10 点 → 90%）；再加 `神·修炼无极0.60` → 1.50 → `max(0,1−1.5)=0` → **100% 必成，22 点**。
→ **结论：任务书候选值「厚积薄发 +20% / 突破通天 +30%」不能直接照搬**，必须先定口径（见 §五 T-3）。

### 为什么不能按任务书说的"不得直接替换 SHA-256"→ 我给的方案

任务书这条约束的**本意是不许"改成永远返回 true"式的假兼容**。正确做法是**把校验升级为真正的多版本校验**，而不是删掉：

**方案 C-1（推荐）：版本探测 + 分支哈希表 + 结构断言不变**

```
1. 用 mods.toml / container 元数据 或 PlayerVariables 的某个版本标志探测本体版本
2. 哈希表改成 Map<版本, Map<类名, SHA>>
   - 9.8  → 现有 9 条（已实测 9/9）
   - 10.4 / 10.20 → 同一份（内层 jar 字节相同），3 条填我实测出的新值
3. 未登记的版本 → 不做硬杀，降级为 WARN + 仍然执行「结构断言」
   （shiqiao 为 boolean、12 个字段为 double —— 这部分 10.20 本来就全过）
4. 保留「类缺失 / 类型不符」为硬错误，那才是真正的不可兼容信号
```

**方案 C-2（保守）：只降级不解锁**——`tizhi` 等结构断言保留，哈希不一致从 `throw` 改成 `WARN`，并在客户端界面显示「本体版本未经验证」。风险是失去保护，但不会崩。

> 需要你选 C-1 还是 C-2。**我建议 C-1**：它既满足「不假兼容」，又让 1.4.18 真正支持 10.20。

### 发现 5｜放大器语义已定论：`amp = 1` 是 **×2.0（+100%）**，不是 +1%

`TianfuLiupai.java:40-41` 注释写「amplifier = 1 就是 +1%」——**这条注释是错的**。

字节码（`BuffLiuCheng1Procedure`，vineflower 可读版）：
```java
JiaCheng += (double) amplifier;                       // :83,94,107,124,149,168,177,192,201,242,267,325,386
Entity2.hurt(..., (float)(ShangHai*(1+A)*(1+C)/(B+1)/(D+1) * (1.0 + JiaCheng)));   // :413
```

`(1.0 + Σ放大器)` → amp=1 → **×2.0**。而 `TianfuLiupai:43` 自己说「本体发剑道 buff 时同样用 amplifier=1」——所以 **本体就是这么设计的**（剑道增幅 = +100%）。

- `TianfuLiupai` 给凡体挂 `AMPLIFIER = 1` → 凡体自带流派增幅 = **×2.0 伤害**，与本体一致，属**正常强度**，不是 bug。

### 7.3 T-3 详解：突破成功率必须重新定口径

本体 `P` 在 [−2, +2]，三转起跌破 0。所以「加成功率」必须先决定作用在哪个量上：

| 方案 | 做法 | 后果 |
|---|---|---|
| A（现状） | 失败率乘算 `P'=1−(1−P)(1−r)` | `P≤0` 时把 0% 变成 r → **四转必败变 90%**，最坏的一条 |
| **B（建议）** | **只在 `P > 0` 时**把 `r` 加进 P，然后整体 clamp 到 `[0, 1]`；`P ≤ 0` 时**天赋不生效** | 与本体"P 是阈值量"的语义一致；高阶天赋不再能撬开"本体判定为不可能"的突破 |
| C | 改成对最终百分比乘算 | 需要本体先 clamp，改动面大，且仍会撬开 P≤0 |

**B 方案配套数值封顶建议**（需你确认）：

| 天赋 | 现效果 | 建议 |
|---|---|---|
| 厚积薄发 | 失败率 −20% | `tupo +0.20` |
| 突破通天 | 失败率 −30% | `tupo +0.30` |
| 修炼如神 | 修炼+60% **且** 突破−40% | **剥离突破**，只留修炼+80% |
| 神·修炼无极 | 修炼+150% **且** 突破−60% | **剥离突破**，只留修炼+150% |
| 极·众道至尊 | 道痕+3000 **且** 修炼+200% **且** 突破−80% | **剥离修炼与突破**，只留道痕 |
| **Σ 上限** | 无 | **`Tupo` 总加成 clamp 到 +0.50**，且仅在 `P>0` 时生效 |

按 B 方案，最多 `0.20+0.30 = 0.50`，四转 `P=−0.74` 时**天赋完全不生效**（本体说着不行就是不行），二转 `P=+0.66` 时升到 1.0 但被 clamp 到 1.0 —— 与任务书「不允许多个天赋叠加后轻易达到 100%」一致。

### 8.2 跨窗口风险：50–70 段安全，**但 20–40 段有真实缺陷**（已修正本报告早期判断）

> ⚠️ 本报告初稿曾写「跨窗口风险不存在」。经对本体 792 个完成型过程逐一解码后，**该结论只对 50–70 段成立，对 20–40 段不成立**。以下是修正后的结论（证据：`30-liangu.md` ②④）。

**本体炼蛊实际分三族**（任务书猜的「20%～40% 检查区间」**真实存在**）：

| 族 | 蛊方数 | 投料窗口 | 说明 |
|---|---:|---|---|
| A | 347 | 只有 `50 ≤ p ≤ 70` | |
| **B** | **351** | **`20 ≤ p ≤ 40` 且 `50 ≤ p ≤ 70`（两段都必投）** | 用**独立标记** `中途加材料1` / `中途加材料` |
| C | 94 | 无投料窗口 | |

**（1）50–70 段：安全，任务书担心的「跳过 50-70」不成立** ✅

`TianfuEffects:272` 的 `inFeedWindow = cur>=50 && cur<=70` 一旦命中就整段停止补点，此后只由本体 `+1` 推进 → `progress == 70` 必然被**精确命中**，窗口停留 ≈31.5 s。单拍最大步长 ≤4 点，远小于窗口宽度 21。**这段设计是对的。**

**（2）20–40 段：未冻结，会产生「静默全损」** ❌ 高

`inFeedWindow` 只写了 50/70，B 族的第一段 `20 ≤ p ≤ 40` **没有被冻结**，后果三条：

- **窗口时长被压缩 3.5 倍**：31.5 s → **9.0 s**，而玩家要在 9 秒内往 5 个槽放**精确数量**的指定物品（如某蛊方第 1 段槽 3 要 64 个）。
- **`progress == 40` 的边界失败判定被 100% 跳过**（`L ≥ 2.2` 时 30/30 相位全跳）。本体在 40 处本会「扣血 + 魂魄 −转数×10 + **明确提示『炼制失败』**」；跳点跨过后这些都不发生。
- **结局更糟**：跳过 40 后玩家继续投第 2 段并成功，到 100 时因 `score1 != 1` → **结算整段跳过 → 进度清零、配方清空、材料与魂魄静默全损、零提示**。

→ 即：**加速把一个「有明确反馈的失败」变成了一个「看起来成功其实全损」**。这必须修。

**（3）另外两个必须知道的硬事实**

- **投料不是可选加成，而是硬性前置**：结算门禁是 `scoreboard("中途加材料") == 1`。窗口内没投料，到 100 时**整段跳过结算**——不扣血、不提示、直接清空。698 个带窗口的蛊方全部如此。
- **完成判定有 1 个例外**：791/792 个类用 `== 100.0`，**唯一例外是 GuFang 234（狐妖蛊）用 `>= 100`**。附属统一按 `== 100.0` 处理是安全的（只会多留 1 点给本体），但要知道这个例外存在。

### 8.3 安全处理方案（只改附属，不动本体）

按性价比排序，**建议 (1)+(2) 一起做**：

**(1) 冻结区间改成所有投料窗口的并集** — 最小改动、收益最大

```java
// TianfuEffects.java:272 现状
boolean inFeedWindow = cur >= 50.0 && cur <= 70.0;
// 建议
boolean inFeedWindow = (cur >= 20.0 && cur <= 40.0)
                    || (cur >= 50.0 && cur <= 70.0);
```
代价：C 族（94 个无窗口蛊方）会多冻结 41 点 ≈61.5 s 的无意义等待；可用 `GuFang` 白名单跳过。

**(2) 单拍最多补 1 点** — 恢复本体「逐点推进」的隐含前提（`bonus` 现可到 2–3 点，正是 (b) 的机理）

```java
int bonus = (int) Math.floor(acc);
if (bonus > 0) { bonus = 1; acc -= 1.0; ... }
```
代价：`L > 1` 时小数累加器会积压，必须同时改溢出策略。二选一：
- `acc = Math.min(acc, 0.999)`：速率被钳到 1 点/拍（等于 +100% 封顶），**最简单最安全**，但高投入天赋收益被削顶；
- `acc` 不钳，但在 `cur` 落进任一窗口前**清空积压**：保住长期平均速率，又保证窗口逐点推进。← **推荐**

**(3) 可选治本**：`cur` 距任一窗口下界 ≤3 点时强制 `bonus = 1`，保证「进入窗口那一步」是逐点进入。

**明确不要做的事**（写下来防误改）：
- **不要**改本体 `==100` / `==40` / `==70` / 窗口区间——那是本体规则，791/792 个类都这么写。
- **不要**把进度推进改成「每 tick 无条件 +」。
- **不要**为规避静默全损而替玩家投料或绕过 `score` 标记——那等于跳过材料检查。
- **不要**写死「槽位 0 有蛊材原石」或「材料是蛊材原石」：材料要求逐蛊方不同（GuFang 617 是槽 0/1/2 各 64 个蛊材原石；GuFang 773 是槽 3–7 的 `FANRENHUNPO×50`/`ERZHUANHUNPO×10`/…）。

### 8.4 炼蛊天赋侧的三个遗留问题

- `liangu_bujie`（天/5）与 `shen_liangu_tianshu`（神/12）**仍带 `GU_CD 0.30 / 0.50`** 蛊虫冷却收益 —— 任务书要求移除，**未执行**。

- 「只选最高等级」后 `Σ ≤ 0.90`，配合 8.3 的 (1)(2) 即可把跨窗口风险彻底消除。

### 8.5 一个未验证风险（第三方 GuFang）

外层门禁实际是 `v.LianGu`；`GuFang != 0.0` 只是「界面开着」的代理（关闭界面时本体会把 `GuFang` 清 0）。但本体 792 个完成型过程按**自己的** `GuFang` 值分派，第三方写的 `9000+i`（六合一）本体不认识 ⇒ **本体的 `+1` 永不发生**，附属会把进度顶到 99 后**永久停在 99**。需实机确认（U-炼蛊-3）。

- **突破成功率**本体是 [−2,+2] 的线性分不是概率，附属按"概率"去乘失败率，把"必败"变成"90% 成功"；
- **互斥表**只覆盖 5 族 12 条，其余 17 个维度全部裸奔，其中 43 条道痕天赋连"同流派只能选最高级"都没约束；
- **炼蛊投料**是硬性前置且有 **两段窗口（20–40 与 50–70）**，附属只冻结了后者 → 351 个蛊方的第一段窗口被压缩到 9 秒，且会跳过 `==40` 的失败判定，把"有提示的失败"变成"静默全损"。

再加上一条 **P0 兼容问题**（9.8 基线的 SHA-256 校验在 10.20 上必崩），1.4.18 的改动重心应当是「**把已有的本体规则接对**」，而不是"加新玩法"——这与任务书最终设计原则完全一致。
