## 一、逐项结论

| 冲突面 | 结论 |

| 本体字段写入 | ⚠️ 见下 |

## 二、Mixin 注入点重合（本次唯一的真冲突）

两个附属注入**完全相同的目标方法、相同的注入点**：

| 目标方法 | 注入点 | tianfu | daotu |
|---|---|---|---|
| `JingJieBaoCunProcedure.execute(Event, LevelAccessor, Entity)` | **HEAD** | ✅ | ✅ |
| `UikongqiaoquedingProcedure.execute(LevelAccessor, Entity)` | **TAIL** | ✅ | ✅ |

两者都用普通 `@Inject`（无 `@Overwrite` / `@Redirect`），且两边配置都是 `defaultRequire: 0`（目标方法缺失时不硬崩）。

**这不会崩游戏**，但两份配置的 `priority` 都是默认值 1000，**执行顺序由 Mixin 内部顺序决定、不保证稳定**。后果是转世与开窍这两个关键时机里，天命与道途的回调先后不确定——目前两者各写自己的 NBT 根，逻辑上互不依赖，所以没暴露；一旦将来任一方开始读对方的写入结果，就会出现"换个加载顺序就换个表现"的幽灵 bug。

**修复**：在各自 `mixins.json` 显式声明优先级，把顺序钉死：

```json
// tianfu.mixins.json
"priority": 900,     // 先生效：天命是开局主流程（转世计数、开窍后的天赋向导）

// daotu.mixins.json
"priority": 1100,    // 后生效：道途在开窍后只发"按 M"提示，依赖天命先跑
```

## 三、本体字段写入交叉

| | 写入字段数 |
|---|---|
| tianfu | 68 |
| daotu | 47 |
| tianyi | **0**（全只读） |

天命与道途有 **24 个字段重叠**：22 个 `daohen_*` / `dahen_*`（两边都是 `+=`，加算兼容），外加：

- `niantou`（念头）、`zhenyuan`（真元）——两者都是「读当前值 → 夹取到 `[0, 上限]` 或 `min(当前+增量, 上限)` → 写回」，**不是写死常量**，单线程内不会互相覆盖。

天意 3.14.0 一个本体字段都不写（相较 3.13.3 的 `WillServer` 曾 `putfield shouyuan`，3.14.0 已移除），所以此前担心的"命烛残尽 vs 世界意志寿元"对冲在本版本不存在。

**结论：字段层面无冲突。**

## 四、其他发现

- 天意 3.14.0 仍在 `TianyiMod` 里保留对 `tianfu` / `daotu` 的检测，启动时打印「检测到旧附属」ERROR。该分支只有 `LOGGER.error`，无禁用逻辑——属**误报**，可忽略。第三方 jar，不改。
- 天命按键原本用 `new KeyMapping(String, int, String)` 三参构造器（已废弃、隐式 `KEYSYM`），本次改为显式 `InputConstants.Type.KEYSYM` 四参，与道途一致。
- 编译期仍有 `@EventBusSubscriber(bus = Bus.MOD)` 的 removal 警告（NeoForge 21.1.x 已标记待删）。**本次未改**：该写法仍可用，改造需把模组总线监听搬到主类构造器，风险大于收益，留待 NeoForge 正式移除时处理。
